# Сценарии приёмочного тестирования

Эти сценарии проверяют Telegram MVP, общий message pipeline и Today Web UI после применения migrations.

## 1. Настройка профиля

Сообщение:

```text
Мой график с 10 до 19, хочу спать в 00:30
```

Ожидается:

- сохраняются начало и конец работы и время сна;
- бот показывает сохранённый профиль;
- следующие планы начинаются после работы и настроенного buffer.

## 2. Добавление целей

Сообщение:

```text
Моя цель: накопить 500000 рублей, научиться рисовать, сделать мобильное приложение
```

Ожидается:

- сохраняются все три цели;
- сумма остаётся частью цели, а не превращается в daily budget;
- `Покажи цели` выводит активные цели понятным текстом.

## 3. Задачи из целей

Сообщение:

```text
Что сделать для целей?
```

Ожидается:

- при наличии целей создаются небольшие связанные действия;
- при отсутствии целей бот мягко предлагает сначала их добавить;
- план выбранной даты перестраивается.

## 4. Задача на сегодня

Сообщение:

```text
Сегодня хочу разобрать документы
```

Ожидается:

- задача получает сегодняшний `target_date`;
- перестраивается план на сегодня;
- задача не появляется в плане на завтра.

## 5. Задача на завтра

Сообщение:

```text
Завтра хочу позаниматься математикой
```

Ожидается:

- задача получает завтрашний `target_date`;
- `Покажи план завтра` включает задачу;
- сегодняшний план её не содержит.

## 6. План дня

Сообщение:

```text
Покажи план
```

Ожидается:

- показывается план на сегодня;
- учитываются work end и sleep time из профиля;
- при неполном профиле используются defaults с понятным пояснением;
- задачи вне доступного времени показаны как not scheduled.

## 7. Выполнение задачи через текст

Сообщение:

```text
Документы сделал
```

Ожидается:

- находится активная задача выбранной даты;
- статус меняется на `done`;
- план перестраивается без выполненной задачи.

## 8. Итог дня

Сообщение:

```text
Итог дня: документы сделал, математику не сделал
```

Ожидается:

- выполненное получает `done`;
- невыполненное остаётся активным;
- бот понятно перечисляет изменения и перестраивает план.

## 9. Перепланирование

Сообщение:

```text
Я задержался до 20
```

Ожидается:

- intent определяется как `reschedule`;
- план начинается от нового времени с buffer;
- задачи, которые больше не помещаются до сна, получают not scheduled.

## 10. Универсальные цели

Сообщение:

```text
Моя цель: улучшить здоровье, чаще видеться с семьёй, написать рассказ, закрыть долг
```

Ожидается:

- сохраняются цели из разных областей;
- предложения не предполагают, что у каждого пользователя только зал, английский или AI-проект.

## 11. Today Web UI

Запуск:

```bash
uvicorn app.main:app --reload
cd web
npm run dev
```

Открыть `http://127.0.0.1:5173` и выбрать временный локальный User ID.

### Пустой день и свободный ввод

Ввод:

```text
Сегодня мало сил, надо оплатить счета и 40 минут поделать проект
```

Ожидается:

- до ввода empty state выглядит нормально;
- Web отправляет `POST /api/message` с `source=web_text`;
- после ответа обновляются plan, tasks, goals и progress;
- AI-summary объясняет результат без технического debug-текста;
- при ошибке введённый текст сохраняется.

### Обратимый checkbox

Ожидается:

- `planned → done` вызывает `PATCH /api/tasks/{task_id}/status` со статусом `done`;
- `done → planned` вызывает тот же endpoint со статусом `planned`;
- checkbox disabled только во время запроса;
- после каждого изменения обновляются tasks, plan и progress;
- mixed state показывает `Сделано X из Y`;
- all-done state показывает «Все задачи закрыты»;
- ошибка не меняет локально показанный статус и объясняется человеческим текстом.

### Living Day composer

Ожидается:

- collapsed composer закреплён снизу и не перекрывает последнюю задачу;
- открытие переводит focus в textarea, `Escape` закрывает sheet и возвращает focus;
- закрытие sheet не очищает draft;
- во время отправки день остаётся видимым, повторный submit заблокирован;
- при успехе draft очищается и показываются только фактические изменения;
- при ошибке sheet раскрыт, полный draft сохранён и доступно «Повторить»;
- технические `intent`, JSON, HTTP status и exception text не видны.

### Checkbox rollback

1. Отключить backend после загрузки дня.
2. Отметить одну задачу выполненной.
3. Убедиться, что pending затрагивает только эту строку.
4. После ошибки checkbox возвращается в исходное состояние.
5. Рядом со строкой появляются «Не удалось сохранить» и «Повторить».

### Фокус, расписание и перегрузка

Ожидается:

- «Фокус дня» содержит не более четырёх строк и опирается только на реальные plan items;
- raw `plan.summary` или LLM output не показывается;
- timeline есть только в «Запланировано»;
- `not_scheduled` показаны в «Без времени» без выдуманного времени;
- день с 10 задачами остаётся читаемым, composer доступен после scroll;
- progress считает все задачи текущего дня, включая выполненные и unscheduled.

### Empty, all done и длинный текст

Ожидается:

- empty day не выглядит ошибкой и не дублирует composer отдельной CTA;
- all done показывает «На сегодня достаточно», полный progress и обратимые строки;
- длинный русский task title занимает не более двух строк, metadata остаётся видимой;
- экран не создаёт горизонтальный scroll на 320, 375, 390, 430 и 560 px.

### Accessibility и устойчивость

Ожидается:

- интерактивные targets не меньше 44×44 px;
- keyboard-only flow позволяет открыть, заполнить, отправить и закрыть composer;
- focus ring видим, ошибки и результат объявляются через `aria-live`;
- `prefers-reduced-motion` отключает перемещение и shimmer;
- при масштабе текста 200% действия остаются доступны;
- initial loading сохраняет геометрию, partial loading не скрывает уже загруженные данные;
- backend unavailable показывает человеческую ошибку и действие «Обновить».

### Изоляция пользователей

Ожидается:

- User A не может изменить задачу User B;
- чужая и несуществующая задача возвращает 404;
- недопустимый status возвращает 422;
- `POST /api/tasks/{task_id}/done` продолжает работать для совместимости.

> [!warning] Временная идентификация
> `user_external_id` предназначен только для локального MVP и не является production authentication.
