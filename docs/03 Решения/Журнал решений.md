# Журнал решений

## D-001 — Фокус на сегодня (Today-first)

Главный экран и главный продуктовый вопрос — что реалистично сделать сегодня.

## D-002 — Свободный текст как основной ввод

Пользователь пишет обычным языком, приложение извлекает структуру и не требует ручного заполнения task tracker.

## D-003 — Единый конвейер сообщений

Telegram, Web и будущий voice transcript проходят через `process_user_message()` и общие services.

## D-004 — Native Ollama для локальной разработки

`LLM_PROVIDER=ollama` использует `/api/chat`; для parser calls по умолчанию передаётся `think=false`.

## D-005 — Living Day / Intelligent Minimal

Living Day заменяет Soft Light Daily Planner как канонический дизайн Today. Экран остаётся светлым, спокойным и mobile-first, но использует холодный нейтральный canvas, muted indigo accent, компактные task rows и result-first иерархию.

Запланированные задачи и задачи без времени разделены. Закреплённый natural-language composer является главным способом сообщить об изменениях. Dead controls, fake times, raw parser data и floating task cards не используются.

Условие пересмотра: повторяющаяся проблема основного цикла, подтверждённая dogfooding, а не желание дополнительной визуальной полировки.

## D-006 — Не делать нативное приложение до dogfooding

Mobile-first Web остаётся быстрым полигоном, пока ежедневная ценность продукта не подтверждена.

## D-007 — Obsidian используется для документации проекта

Vault хранится непосредственно в `docs/` рядом с кодом. Это не означает пользовательскую интеграцию AI Life Planner с Obsidian.

## D-008 — Backend контролирует статус задачи

Checkbox вызывает `PATCH /api/tasks/{task_id}/status`, а изменение выполняет `task_service`. Допустимы только `planned` и `done`; запрос фильтруется по `task_id + user_id`. LLM не меняет статус напрямую.

## D-009 — Один текущий продуктовый фокус

До окончания dogfooding новые идеи отправляются в backlog. Текущий этап меняется только после явного решения и обновления roadmap.

## D-010 — LLM понимает ограничения, backend строит расписание

Parser или LLM извлекает только структурированный смысл сообщения: operation, date, duration, fixed/flexible semantics, preferred window и ограничения. Окончательное время рассчитывает deterministic backend scheduler на timezone-aware `datetime`.

Рабочее время, сон, fixed events и существующие plan intervals формируют availability. Fixed элементы не перемещаются молча, overlaps запрещены, отсутствие подходящего окна сохраняется как честный unscheduled result. При конфликте или неоднозначной ссылке mutation откатывается и пользователь получает clarification.

Telegram, Web и будущий voice transcript используют один `process_user_message()` pipeline. Для voice меняется только шаг speech-to-text; отдельный scheduler не создаётся.

Условие пересмотра: dogfooding показывает, что прозрачной deterministic scoring недостаточно и нужен более сложный solver. До такого подтверждения OR-Tools или LLM scheduling не добавляются.

## D-011 — Message lifecycle является persistent и атомарным

Неоднозначные сообщения хранятся как user-scoped pending interactions с expiry. Сильные изменения требуют confirmation, привязанного к plan version. Message submit имеет user-scoped idempotency key, а финальный ответ возвращает один согласованный `DaySnapshot` для атомарного обновления Web UI.

Причина: chat-only context, повторный POST и waterfall GET создавали риск дублей, stale state и частично обновлённого Today.

## D-012 — Routine MVP ограничен и материализуется лениво

Поддерживаются только daily, weekdays и selected weekdays. Occurrence создаётся при построении DayPlan, уникальна по routine/date и дальше планируется как обычная fixed или flexible task. Создание routine требует confirmation.

Условие пересмотра: dogfooding подтверждает необходимость исключений, сложных интервалов или массового редактирования серий. До этого полноценный recurrence engine не строится.

## D-013 — Рабочий график не является задачей

Постоянный рабочий график хранится в `User`, а исключение конкретного дня — в `DayPlan`. Оба варианта формируют busy interval для scheduler, но не создают `Task`.

Явная дата означает дневную доступность и не меняет профиль. Двусмысленная команда вроде «добавь работу с 9 до 18» требует persistent clarification до мутации. Повтор идентичного графика идемпотентен и возвращает `no_change`.

Причина: смешивание контекста доступности с пользовательскими делами создавало фиктивную часовую задачу, неверный focus и ложный plan diff.
