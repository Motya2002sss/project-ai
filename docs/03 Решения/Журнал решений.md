# Журнал решений

## D-001 — Фокус на сегодня (Today-first)

Главный экран и главный продуктовый вопрос — что реалистично сделать сегодня.

## D-002 — Свободный текст как основной ввод

Пользователь пишет обычным языком, приложение извлекает структуру и не требует ручного заполнения task tracker.

## D-003 — Единый конвейер сообщений

iOS, frozen Telegram/Web и будущий voice transcript проходят через `process_user_message()` и общие services.

## D-004 — Native Ollama для локальной разработки

`LLM_PROVIDER=ollama` использует `/api/chat`; для parser calls по умолчанию передаётся `think=false`.

## D-005 — Living Day / Intelligent Minimal

Living Day заменяет Soft Light Daily Planner как канонический дизайн Today. Экран остаётся светлым, спокойным и mobile-first, но использует холодный нейтральный canvas, muted indigo accent, компактные task rows и result-first иерархию.

Запланированные задачи и задачи без времени разделены. Закреплённый natural-language composer является главным способом сообщить об изменениях. Dead controls, fake times, raw parser data и floating task cards не используются.

Условие пересмотра: повторяющаяся проблема основного цикла, подтверждённая dogfooding, а не желание дополнительной визуальной полировки.

## D-006 — Не делать нативное приложение до dogfooding (заменено D-014)

Mobile-first Web остаётся быстрым полигоном, пока ежедневная ценность продукта не подтверждена.

Решение заменено явным iOS-first направлением в D-014. Запись сохранена как история принятого ранее ограничения.

## D-007 — Obsidian используется для документации проекта

Vault хранится непосредственно в `docs/` рядом с кодом. Это не означает пользовательскую интеграцию AI Life Planner с Obsidian.

## D-008 — Backend контролирует статус задачи

Checkbox вызывает `PATCH /api/tasks/{task_id}/status`, а изменение выполняет `task_service`. Допустимы только `planned` и `done`; запрос фильтруется по `task_id + user_id`. LLM не меняет статус напрямую.

## D-009 — Один текущий продуктовый фокус

До окончания dogfooding новые идеи отправляются в backlog. Текущий этап меняется только после явного решения и обновления roadmap.

## D-010 — LLM понимает ограничения, backend строит расписание

Parser или LLM извлекает только структурированный смысл сообщения: operation, date, duration, fixed/flexible semantics, preferred window и ограничения. Окончательное время рассчитывает deterministic backend scheduler на timezone-aware `datetime`.

Рабочее время, сон, fixed events и существующие plan intervals формируют availability. Fixed элементы не перемещаются молча, overlaps запрещены, отсутствие подходящего окна сохраняется как честный unscheduled result. При конфликте или неоднозначной ссылке mutation откатывается и пользователь получает clarification.

iOS, frozen Telegram/Web и будущий voice transcript используют один `process_user_message()` pipeline. Для voice меняется только шаг speech-to-text; отдельный scheduler не создаётся.

Условие пересмотра: dogfooding показывает, что прозрачной deterministic scoring недостаточно и нужен более сложный solver. До такого подтверждения OR-Tools или LLM scheduling не добавляются.

## D-011 — Message lifecycle является persistent и атомарным

Неоднозначные сообщения хранятся как user-scoped pending interactions с expiry. Сильные изменения требуют confirmation, привязанного к plan version. Message submit имеет user-scoped idempotency key, а финальный ответ возвращает один согласованный `DaySnapshot` для атомарного обновления клиента.

Причина: chat-only context, повторный POST и waterfall GET создавали риск дублей, stale state и частично обновлённого Today.

## D-012 — Routine MVP ограничен и материализуется лениво

Поддерживаются только daily, weekdays и selected weekdays. Occurrence создаётся при построении DayPlan, уникальна по routine/date и дальше планируется как обычная fixed или flexible task. Создание routine требует confirmation.

Условие пересмотра: dogfooding подтверждает необходимость исключений, сложных интервалов или массового редактирования серий. До этого полноценный recurrence engine не строится.

## D-013 — Рабочий график не является задачей

Постоянный рабочий график хранится в `User`, а исключение конкретного дня — в `DayPlan`. Оба варианта формируют busy interval для scheduler, но не создают `Task`.

Явная дата означает дневную доступность и не меняет профиль. Двусмысленная команда вроде «добавь работу с 9 до 18» требует persistent clarification до мутации. Повтор идентичного графика идемпотентен и возвращает `no_change`.

Причина: смешивание контекста доступности с пользовательскими делами создавало фиктивную часовую задачу, неверный focus и ложный plan diff.

## D-014 — iOS-first и единый backend contract

**Решение:** iOS является единственным основным пользовательским клиентом первого релиза. Android подключается после проверки iOS-версии. Web и Telegram не удаляются, но замораживаются и больше не определяют product roadmap.

FastAPI, PostgreSQL и Planning Engine являются единственным source of truth для tasks, plans, scheduling, routines, work availability, goals, clarification, confirmation, conflicts и будущих plan changes. Клиенты хранят только cache и draft.

Все новые клиенты используют один backend contract:

```text
iOS → FastAPI → interpretation → clarification / confirmation
    → planning engine → PostgreSQL → DaySnapshot / PlanDiff → iOS
```

Voice не получает отдельную planning logic:

```text
audio → transcription → тот же message pipeline → planning engine
```

**Причина:** развитие нескольких интерфейсов до проверки основного пользовательского опыта размывает фокус, а перенос parser/scheduler logic в mobile создаёт несовместимые источники состояния.

**Следствие:** новый продуктовый код начинается с Mobile API и iOS. Изменения frozen Web/Telegram допускаются только для сохранения совместимости или по отдельному решению.

## D-015 — P0 auth boundary для локального iOS dogfooding

Mobile API v1 использует `Authorization: Bearer` и server-configured identity. Клиент не передаёт `user_external_id` ни в path, ни в body. Один локальный token соответствует одному dogfood user.

Это временная граница только для local dogfooding. Для TestFlight она заменяется проверкой Sign in with Apple identity и server-side mapping `(provider, subject) → user_id`. Общий статический token не является production authentication.

## D-016 — Mobile mutation возвращает согласованное состояние

Capture, interaction response и task status mutation возвращают backend-calculated result. Capture и interaction содержат status, factual `PlanDiff` и атомарный `DaySnapshot`; task status содержит изменённую task, factual diff и перестроенный snapshot.

Mobile не выполняет waterfall `POST → GET tasks → GET plan → GET goals` и не рассчитывает current task, conflicts или расписание самостоятельно.

## D-017 — Mobile Product & Design Handoff v1 зафиксирован

**Решение:** [[04 Дизайн/Mobile Product & Design Handoff v1]] становится product/design source of truth для mobile v1 и заменяет визуальные детали раннего Living Day exploration из D-005 там, где документы расходятся.

Финальное направление использует спокойный paper background, матовый burgundy accent, системную iOS-типографику, единую timeline на Today, quick completion слева, task details без промежуточного post-completion экрана и Capture как text/voice input, а не AI-chat.

Это решение фиксирует целевой mobile v1, но не расширяет текущий engineering P0. Первый dogfooding остаётся узким Today vertical slice по [[07 Техническая документация/Mobile API Contract v1]]. Onboarding, Week, Path, Profile mutations, Voice/STT, general Undo и workout tracker переходят в P1 contract slices и не должны блокировать нативный Today.

**Причина:** Engineering и Mobile Agents должны видеть один согласованный UX без возврата отвергнутых кнопок, dashboard-паттернов, AI-decoration и ранней indigo-палитры, сохраняя при этом текущий ограниченный roadmap.

**Условие пересмотра:** повторяющаяся проблема реального iPhone dogfooding, а не желание дополнительной визуальной полировки.

## D-018 — Production identity отделена от dogfood auth

**Решение:** все production-capable endpoints используют opaque rotating session из `/api/v2`. Internal `users.id` определяется только server-side через проверенный Apple subject. Статический Mobile API v1 bearer остаётся локальным compatibility boundary и запрещён runtime validation в staging/production.

На iOS access/refresh credentials хранятся только в SecureStore. Public user UUID используется только как AsyncStorage namespace; cache и draft никогда не являются глобальными. Refresh rotation создаёт поколения внутри device family, а reuse старого refresh отзывает family.

**Причина:** общий dogfood token и глобальные cache keys не дают multi-user isolation, logout/revocation и безопасный TestFlight lifecycle.

**Следствие:** production mobile flow подключается только к authenticated v2 contracts. Нельзя направить Apple session в dogfood `/api/v1` или сохранить v1 snapshot в namespace production user. Account deletion остаётся release blocker до реализации Apple authorization-code exchange/revocation и проверки на release build.

**Условие пересмотра:** только документированное изменение Apple platform requirements или подтверждённая уязвимость текущей opaque-session модели.
