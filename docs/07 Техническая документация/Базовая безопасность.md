# Базовая безопасность

AI Life Planner развивается как потенциальный коммерческий продукт. Безопасность, приватность и изоляция данных входят в базовые требования, а не откладываются как необязательная полировка.

## Секреты

Никогда не коммить:

- `.env` и `.env.*`, кроме `.env.example`;
- Telegram bot tokens;
- OpenAI и другие LLM API keys;
- реальные database passwords;
- private URLs со встроенными credentials;
- cookies, session tokens и Authorization headers;
- logs с секретами или полным dump конфигурации.

Для локальных секретов используй `.env`. В `.env.example` допустимы только безопасные placeholders и пустые значения для реальных tokens.

Обязательные ignore rules:

- `.env` и `.env.*` с исключением `.env.example`;
- `.venv/`;
- `node_modules/`;
- `__pycache__/` и `.pytest_cache/`;
- `dist/` и `build/`;
- `*.db`, `*.sqlite`, `*.sqlite3`;
- `*.log` и `logs/`;
- персональное состояние Obsidian: `workspace*.json`, plugins и cache.

## Логирование

Не логировать:

- Telegram token;
- LLM API key;
- Authorization headers;
- cookies;
- raw `.env`;
- полный database URL с password.

Если конфигурацию нужно показать при отладке, чувствительные части маскируются:

```text
sk-...abcd
postgresql://user:***@host/db
```

## Проверка перед commit и push

Для кодовых изменений выполнить релевантные команды:

```bash
alembic upgrade head
python scripts/check_mvp.py
python - <<'PY'
from app.bot.main import dp
from app.main import app
print("bot and app import ok")
PY
pytest
```

Перед commit проверить:

```bash
git status
git diff --stat
git diff --cached --name-only
git diff --cached
```

Остановиться, если в staging есть `.env`, tokens, реальные passwords, cookies, private URLs, сгенерированные artifacts или несвязанные изменения.

Перед push:

```bash
git remote -v
git branch --show-current
git push -u origin HEAD
```

Push выполняется только в проверенный intended remote. После push SHA удалённой ветки сверяется с локальным `HEAD`.

## FastAPI

- Request body валидируется через Pydantic schemas.
- Пользовательскому вводу нельзя доверять.
- Responses не должны раскрывать лишние внутренние поля.
- Destructive endpoints требуют явного продуктового основания и безопасного UX.
- Production CORS wildcard запрещён.
- Local CORS ограничен известными origins, например `http://localhost:5173` и `http://127.0.0.1:5173`.
- Debug endpoints не должны раскрывать env, config, tokens, stack traces или credentials.
- Ошибки для пользователя должны быть понятными и не раскрывать internals.
- API endpoints остаются thin layer и вызывают services, parser и planner.

## Безопасность базы данных

- Schema changes выполняются только через Alembic migrations.
- Repair SQL должен быть idempotent, когда это возможно.
- Пользовательские данные нельзя удалять без явного указания.
- Docker volumes нельзя удалять как shortcut.
- `drop_all()` и `create_all()` запрещены в runtime application code.
- Destructive operations объясняются и проверяются до выполнения.

## Изоляция пользователей

Пользователь должен видеть и менять только собственные profile, goals, tasks, routines, interactions, idempotency receipts и plans.

Правила текущего MVP:

- Telegram user разрешается через `get_or_create_user()`.
- Web/API user временно разрешается через `user_external_id`.
- `user_external_id` не является production authentication.
- Today Web UI хранит этот identifier в `localStorage`; это не proof of identity.
- Service queries для пользовательских данных включают фильтр `user_id`.
- Task mutation фильтрует запись одновременно по `task_id` и `user_id`.
- Clarification/confirmation lookup, routine materialization и idempotency lookup всегда включают `user_id`.
- Expired, resolved или stale interaction не может повторно применить mutation.
- Чужая и несуществующая задача возвращает одинаковый 404, не раскрывая наличие данных.
- До публичного deployment Web API обязан получить явную authentication strategy.

Правила Mobile API v1:

- iOS не передаёт user id в path или body;
- local dogfooding использует `Authorization: Bearer` с `MOBILE_DOGFOOD_TOKEN` из `.env`;
- iOS получает shared secret только через untracked local provisioning, хранит его в Keychain и не включает в source code;
- physical-device dogfooding передаёт bearer token только по HTTPS;
- token сравнивается constant-time и никогда не логируется;
- server сам разрешает token в `MOBILE_DOGFOOD_USER_EXTERNAL_ID`;
- frozen compatibility API блокирует `mobile:*` и configured mobile identity;
- отсутствие или неверный token не создаёт пользователя и не раскрывает данные;
- общий dogfood token запрещён для TestFlight и production;
- TestFlight требует проверяемую внешнюю identity, предпочтительно Sign in with Apple, и server-side mapping к `users.id`.

## Безопасность LLM

При включённом LLM parser:

- модель возвращает только structured JSON;
- JSON валидируется через Pydantic;
- invalid output, timeout и provider errors приводят к mock fallback;
- input, output и timeout ограничены настройками;
- native Ollama parser использует `/api/chat` и по умолчанию `LLM_OLLAMA_THINK=false`;
- LLM не выполняет команды;
- LLM не является источником правды для database writes;
- `.env`, tokens, credentials и внутренний config не отправляются модели;
- prompt injection не может раскрывать secrets или обходить backend validation;
- fallback logs содержат только provider, model, error class и sanitized message.

## Надёжность message processing

- Web ограничивает message request по времени и сохраняет draft при timeout.
- LLM timeout короче общего request budget; provider retries отключены внутри одного submit.
- Повтор submit с тем же `request_id` возвращает сохранённый результат и не создаёт вторую mutation.
- Confirmation проверяет plan version перед применением.
- Транзакция откатывается при conflict или нарушении no-overlap invariant.
- Mobile при transport timeout повторяет capture с тем же `request_id`, а не создаёт новый.

## Зависимости

- Dependency добавляется только при ясной продуктовой или инженерной причине.
- Предпочтительны поддерживаемые packages с активными security updates.
- Пакеты с external telemetry или secrets требуют отдельного review.
- Dependency changes должны быть небольшими и объяснимыми.
- `npm audit` и другие scanners оцениваются осознанно; автоматический массовый upgrade без проверки запрещён.

## Перед production

- добавить production authentication;
- разделить local, staging и production config;
- отключить debug mode;
- настроить production-safe CORS;
- добавить structured logging с secret masking;
- определить backup и migration rollback procedures;
- добавить rate limits для bot и API;
- проверить dependency vulnerabilities;
- настроить monitoring parser failures, database errors и критичных workflows;
- документировать incident response для leaked tokens и повреждения данных.
