# AI Life Planner — Mobile Product & Design Handoff v1

**Статус:** product/design source of truth для Engineering Agent и будущего Mobile Agent
**Зафиксировано:** 10 августа 2026
**Назначение:** передать утверждённую мобильную концепцию без необходимости читать историю дизайн-обсуждения
**Ограничение:** этот документ не проектирует backend, не выбирает mobile framework и не разрешает переосмысливать утверждённый UX

---

## 1. Product concept

AI Life Planner — мобильное приложение, которое превращает обычную человеческую речь о делах, ограничениях и целях в реалистичный план жизни.

Пользователь не должен вручную управлять слотами, приоритетами, категориями и зависимостями. Он пишет или говорит, например:

- «Сегодня после работы хочу в зал»;
- «Хочу за год стать Senior-разработчиком»;
- «Сегодня задержусь на работе до восьми»;
- «Я устал, перенеси английский на завтра».

Приложение понимает намерение, при критической неоднозначности задаёт один короткий вопрос, размещает действия во времени, показывает получившийся день и адаптирует его при изменениях.

### Какую проблему решает

Обычные планировщики перекладывают на человека работу по организации собственной жизни. AI Life Planner забирает эту работу на себя: человеку остаётся сообщить контекст, выполнить понятное следующее действие и при необходимости рассказать, что изменилось.

### Чем продукт не является

- **Не todo list:** пользователь не сортирует вручную длинный список задач.
- **Не календарь:** пользователь не строит расписание перетаскиванием блоков.
- **Не task manager:** нет Jira-подобных статусов, приоритетов и служебных полей.
- **Не AI-чат:** AI не является главным визуальным объектом; важен изменившийся план, а не история сообщений.

### Основной пользовательский цикл

`CAPTURE → UNDERSTAND → PLAN → DO → ADAPT`

1. Пользователь говорит или пишет естественным языком.
2. Система понимает запрос либо задаёт один необходимый вопрос.
3. Система создаёт или перестраивает план.
4. Пользователь видит, что делать сейчас, и выполняет действие.
5. Фактический результат обновляет план и прогресс долгосрочной цели.

### Ощущение от продукта

Спокойный персональный ежедневник: mobile-native, собранный, тёплый, лёгкий и взрослый. Приложение должно снижать тревогу от планирования, а не демонстрировать сложность AI.

## 2. Product surface

- Основной продукт — **мобильное приложение**, не Web и не Telegram-интерфейс.
- Первый клиент — **iOS** для реального dogfooding на iPhone.
- Android — позже; базовая структура должна оставаться переносимой, но Android-specific polish не входит в первый iOS dogfooding.
- Дизайн — mobile-first для референсного viewport `390×844`, с обязательной проверкой узкой геометрии `360×800`.
- Web-прототип и Telegram могут быть техническими поверхностями, но **не определяют UX мобильного продукта**.
- Существующий FastAPI backend сохраняется. Этот документ описывает только ожидания mobile UX от backend и не задаёт его внутреннюю архитектуру.

## 3. Утверждённые экраны

### 3.1 Onboarding — «Расскажите, как вы живёте»

**Цель**
Получить достаточный жизненный контекст без анкеты, чтобы собрать первый реалистичный план.

**Что пользователь должен понять за 3–5 секунд**
Можно обычными словами рассказать про рабочий день, свободное время и цели; заполнять сложную форму не нужно.

**Контент**

- системный header и back, если экран открыт из Profile;
- заголовок «Расскажите, как вы живёте»;
- короткая подсказка: «Обычный день, свободное время и цели — своими словами»;
- единая область рассказа;
- действия «Записать голос» и «Написать»;
- основная кнопка «Собрать мой план».

**Основные действия**

- записать рассказ голосом;
- написать или изменить рассказ;
- запустить сбор первого плана.

**Вторичные действия**

- вернуться назад без изменения существующего плана.

**После действия**

- голос открывает Voice Capture sheet в onboarding-контексте;
- текст открывает Text Capture sheet с текущим рассказом как draft;
- «Собрать мой план» показывает компактное processing-состояние и затем открывает первый собранный план.

**Empty state**
Область рассказа пустая, видны короткий пример и две равноправные точки входа: голос и текст. Не показывать заранее заполненные формы, категории и поля времени.

**Loading**
Кнопка временно меняется на «Собираю план…», повторное нажатие блокируется. Полноэкранная AI-анимация не нужна.

**Error**
Короткое человеческое сообщение рядом с основной кнопкой: «Не получилось собрать план. Попробовать ещё раз». Draft не теряется.

**Особые состояния**

- существующий пользователь может открыть этот же экран из Profile как «Мой распорядок»;
- при критически неполном рассказе вместо догадки появляется один Clarification sheet.

**Что нельзя добавлять**

- пошаговую анкету на десятки экранов;
- ручной выбор категорий, приоритетов и временных слотов;
- персонажа AI, чат-пузырьки и историю диалога;
- обязательные поля, которые можно понять из рассказа.

### 3.2 Первый собранный план — «Ваш ритм на август»

**Цель**
Показать пользователю, как его рассказ превратился в понятный жизненный ритм, прежде чем открыть Today.

**Что пользователь должен понять за 3–5 секунд**
Система поняла три цели, определила разумную частоту действий и построила базовый вечер.

**Контент**

- заголовок «Ваш ритм на август»;
- пояснение, что план опирается на рабочий день и будет меняться вместе с пользователем;
- цель «Senior-разработчик» — 4 раза в неделю;
- цель «Набрать 6 кг» — 3 тренировки плюс питание;
- цель «Сесть на шпагат» — 5 коротких занятий по 12 минут;
- блок «Базовый вечер»: тренировка, ужин, растяжка;
- основная кнопка «Начать».

**Основные действия**

- принять первый план и перейти в Today.

**Вторичные действия**

- вернуться к рассказу и изменить исходный контекст.

**После действия**
«Начать» открывает Today с первым построенным днём.

**Empty state**
Не применим: экран появляется только после успешной сборки.

**Loading**
До появления экрана остаётся на onboarding-кнопке; сам экран не должен показывать скелетон без содержимого.

**Error**
Пользователь остаётся в onboarding с сохранённым draft и возможностью повторить.

**Особые состояния**
Если требуется одно уточнение, Clarification появляется до этого экрана.

**Что нельзя добавлять**

- техническое объяснение рассуждений AI;
- десятки метрик и прогнозов;
- ручное редактирование каждого слота прямо на этом экране;
- обещание математически точного результата.

### 3.3 Today — «Сегодня»

**Цель**
Быть главным ежедневным экраном: показать текущее действие, следующие события и быстрый способ сообщить изменение.

**Что пользователь должен понять за 3–5 секунд**

1. Что делать прямо сейчас.
2. Что будет следующим.
3. Когда закончится запланированная часть дня.
4. Изменился ли план.
5. Где быстро сказать или написать новое обстоятельство.

**Контент**
Header с датой и календарём, временная линия дня, текущая задача, будущие задачи, завершённые задачи, свободное время, capture-контролы и нижняя навигация.

**Основные действия**

- открыть задачу нажатием на её содержание;
- быстро завершить задачу круглой галочкой слева;
- открыть Text Capture;
- открыть Voice Capture.

**Вторичные действия**

- открыть Week через календарь;
- перейти в Path или Profile;
- отменить последнее значимое изменение через «Вернуть».

**После действия**

- task tap открывает Task Details;
- checkbox завершает действие на месте и обновляет связанную цель;
- capture после обработки возвращает в Today с перестроенной линией;
- Week открывается как nested screen.

**Empty state**
Если план ещё не создан — короткое приглашение рассказать о своём дне и основная точка capture. Не показывать пустой dashboard.

**Loading**
При первичной загрузке допустим тихий skeleton только в геометрии timeline. Capture и навигация остаются доступными, если сохранён локальный день.

**Error**
Показывать последний сохранённый план и неблокирующую строку: «Не удалось обновить день». Действие «Повторить» — только если оно реально нужно.

**Особые состояния**

- plan changed с коротким diff-confirmation и Undo;
- conflict;
- clarification sheet;
- all done;
- offline с локально сохранённым днём;
- optimistic completion rollback при ошибке сохранения.

**Что нельзя добавлять**

- dashboard-метрики;
- отдельные карточки NOW/UP NEXT только ради заполнения экрана;
- статистику всех целей;
- фильтры и категории;
- постоянный AI-баннер;
- ручное перетаскивание задач;
- чат с AI.

### 3.4 Task Details — подробности задачи

**Цель**
Дать достаточно информации для выполнения конкретного действия.

**Что пользователь должен понять за 3–5 секунд**
Что именно нужно сделать, в какое время, как это связано с целью и какой план выполнения.

**Контент**

- back;
- тип задачи и время;
- название;
- связанная цель;
- последовательный план;
- нижняя основная кнопка «Завершить задачу».

**Основные действия**

- выполнить задачу и нажать «Завершить задачу».

**Вторичные действия**

- вернуться в Today без завершения.

**После действия**
Задача завершается, экран без промежуточного результата возвращается в Today, строка становится приглушённой, галочка — заполненной, Path получает новый прогресс.

**Empty state**
Если у задачи нет дополнительного плана, показываются только название, время, связь с целью и кнопка завершения. Не создавать пустую секцию «План».

**Loading**
Локальные данные показываются сразу; обновление деталей не должно блокировать back.

**Error**
Если completion не сохранился, вернуть задачу в незавершённое состояние и показать короткое «Не удалось сохранить. Повторить».

**Особые состояния**

- уже завершённая задача открывается read-only;
- workout-task использует отдельное содержимое Workout Details.

**Что нельзя добавлять**

- кнопки «Продолжить», «Сказать, как вышло», «Изменить вручную»;
- итоговый экран после завершения;
- технический AI-комментарий;
- служебные поля task manager.

### 3.5 Workout Details — тренировка

**Статус:** утверждённый экран целевого mobile v1. Реализация workout logging относится к P1; история программы и расширенная аналитика — Later.

**Цель**
Позволить пройти тренировку по составленному плану и зафиксировать фактический результат каждого подхода.

**Что пользователь должен понять за 3–5 секунд**
Какая тренировка запланирована, с какой целью она связана, какие упражнения, веса, подходы и повторения нужно выполнить.

**Контент**

- header «Тренировка» и длительность;
- название «Тренировка на силу»;
- цель «Набрать 6 килограммов»;
- список упражнений;
- план каждого упражнения;
- строки подходов: номер, фактический вес, фактические повторения;
- кнопка «Завершить тренировку».

**Основные действия**

- изменить вес и повторения прямо в строке подхода;
- завершить тренировку.

**Вторичные действия**

- вернуться, сохранив введённый draft локально.

**После действия**
Фактические результаты сохраняются, пользователь возвращается в Today, цель по набору веса получает прогресс.

**Empty state**
Если программа не загрузилась, не показывать пустую таблицу: коротко сообщить «Программа тренировки пока недоступна» и оставить back.

**Loading**
Сохранённая программа показывается сразу. Синхронизация результата не блокирует ввод.

**Error**
Draft подходов остаётся на устройстве. Пользователь видит «Результаты сохранены на телефоне и отправятся позже».

**Особые состояния**
Если в четвёртом подходе выполнено 5 повторений вместо 6, интерфейс просто хранит `5` как факт. Допустимо аккуратное бордовое выделение изменённого значения, но не предупреждение.

**Что нельзя добавлять**

- оценку «плохо» или «ошибка» за невыполненный повтор;
- обязательный отчёт «как вышло» после тренировки;
- отдельную кнопку ручного редактирования — поля уже редактируемые;
- графики и advanced workout analytics в P0.

### 3.6 Week — «Неделя»

**Цель**
Дать спокойный обзор ближайших дней без превращения приложения в календарный редактор.

**Что пользователь должен понять за 3–5 секунд**
Как распределены основные действия по неделе и что запланировано на выбранный день.

**Контент**

- back в Today;
- заголовок «Неделя» и диапазон дат;
- компактная полоса из семи дней;
- список временных действий выбранного дня;
- capture-контролы в нижней thumb zone.

**Основные действия**

- выбрать день;
- открыть Text/Voice Capture для изменения плана.

**Вторичные действия**

- вернуться в Today.

**После действия**
Выбор дня заменяет список без отдельной навигации. Capture после применённого replanning возвращает в Today, чтобы показать результат.

**Empty state**
«На этот день ничего не запланировано» плюс свободное время и capture. Не предлагать вручную заполнять календарь.

**Loading**
Показывать локально сохранённую неделю; тихо синхронизировать изменения.

**Error**
Последний сохранённый обзор остаётся доступен.

**Особые состояния**
Завершённые действия приглушены и имеют галочку. Текущий день отмечен маленькой бордовой точкой.

**Что нельзя добавлять**

- drag-and-drop;
- изменение длительности жестами;
- сложную календарную сетку;
- постоянные категории и цветовые легенды.

### 3.7 Path — «Путь»

**Цель**
Показать связь между выполненными действиями и долгосрочными целями.

**Что пользователь должен понять за 3–5 секунд**
Какие цели активны, насколько продвинулся пользователь и какое последнее действие повлияло на каждую цель.

**Контент**

- цели «Стать Senior-разработчиком», «Набрать 6 килограммов», «Сесть на шпагат»;
- процент;
- тонкая progress-line с этапами и маркером;
- последнее изменение и источник прогресса;
- capture и основная нижняя навигация.

**Основные действия**

- просмотреть прогресс;
- открыть capture.

**Вторичные действия**

- перейти в Today или Profile.

**После действия**
При открытии линия и процент мягко переходят к текущему значению. Завершение связанной задачи автоматически меняет progress.

**Empty state**
Если целей нет — одно спокойное приглашение рассказать, чего пользователь хочет достичь. Не показывать нулевой dashboard.

**Loading**
Последние сохранённые значения остаются видимыми.

**Error**
Показать сохранённый прогресс без ложного пересчёта.

**Особые состояния**
Проценты являются понятной продуктовой моделью прогресса, но не должны сопровождаться псевдонаучной аналитикой.

**Что нельзя добавлять**

- advanced goal analytics в P0;
- KPI-grid;
- соревновательные рейтинги;
- яркие разноцветные категории;
- отдельный AI-анализ каждой цели на основном экране.

### 3.8 Profile — «Профиль»

**Цель**
Дать доступ к личному распорядку, целям и системным настройкам, не смешивая их с Today.

**Что пользователь должен понять за 3–5 секунд**
Где изменить исходный жизненный контекст, открыть цели и управлять доступами.

**Контент**

- имя и небольшой буквенный avatar-mark;
- «Мой распорядок»;
- «Цели и планы»;
- «Уведомления»;
- «Данные и доступ»;
- нижняя навигация.

**Основные действия**

- открыть и обновить распорядок;
- открыть Path;
- открыть настройки уведомлений и данных, когда они реализованы.

**Вторичные действия**

- перейти в Today.

**После действия**
«Мой распорядок» открывает onboarding-структуру с существующим рассказом; «Цели и планы» открывает Path.

**Empty state**
До появления профиля показывается локальный нейтральный placeholder без большой декоративной карточки.

**Loading**
Локальные данные сразу, синхронизация в фоне.

**Error**
Настройки, не требующие сети, остаются доступны.

**Особые состояния**
Неактивные P1-интеграции не должны выглядеть как работающие действия в P0.

**Что нельзя добавлять**

- большую hero-аватарку;
- достижения и gamification;
- dashboard аккаунта;
- дублирование Today-метрик.

### 3.9 Text Capture sheet

**Цель**
Принять естественный текстовый запрос без открытия AI-чата.

**Что пользователь должен понять за 3–5 секунд**
Можно просто описать изменение дня или жизненный контекст обычной фразой.

**Контент**

- контекстный заголовок: «Что изменилось?» либо «Расскажите о себе»;
- textarea с draft;
- короткая подсказка;
- одно основное действие: «Обновить день» либо «Сохранить рассказ»;
- закрытие sheet.

**Основные действия**
Изменить draft и отправить.

**Вторичные действия**
Закрыть sheet без отправки.

**После действия**
Запрос переходит в processing и затем приводит к applied, clarification, conflict, unsupported или error.

**Empty state**
Пустой текст не отправляется; основной action disabled.

**Loading**
Action показывает «Обновляю…», draft остаётся видимым.

**Error**
Sheet остаётся открыт, draft сохраняется, появляется короткое сообщение и retry.

**Особые состояния**
После applied sheet закрывается, открывается Today и показывается краткий результат изменения.

**Что нельзя добавлять**
Историю сообщений, роль assistant, streaming-рассуждения и технические параметры.

### 3.10 Voice Capture sheet

**Цель**
Дать самый быстрый способ Capture голосом.

**Что пользователь должен понять за 3–5 секунд**
Запись идёт, приложение слушает и показывает распознанную фразу.

**Контент**

- состояние «Слушаю»;
- заголовок «Говорите как обычно»;
- спокойная бордовая waveform;
- transcript;
- «Готово»;
- close/cancel.

**Основные действия**
Остановить и подтвердить распознанную фразу.

**Вторичные действия**
Отменить запись. Возможность исправить transcript должна остаться в том же sheet; точный production-control пока OPEN.

**После действия**
Запрос обрабатывается тем же Capture flow, что и текст. Voice не создаёт отдельную историю.

**Empty state**
Если речь не распознана: «Не расслышал. Попробовать ещё раз» без создания пустого запроса.

**Loading**
После подтверждения waveform останавливается, action показывает обработку.

**Error**
Transcript сохраняется, если уже получен; пользователь может повторить или перейти к тексту.

**Особые состояния**
Onboarding voice записывает жизненный контекст; Today/Week voice описывает изменение плана.

**Что нельзя добавлять**
Полноэкранного голосового ассистента, AI-avatar, историю разговора и отдельный voice-tab.

### 3.11 Clarification sheet

**Цель**
Не позволить системе угадывать критически неоднозначное намерение.

**Что пользователь должен понять за 3–5 секунд**
Системе нужен ровно один выбор, чтобы корректно применить запрос.

**Контент**

- один короткий вопрос;
- 2–3 понятных варианта ответа;
- возможность ответить своими словами;
- cancel.

**Основные действия**
Выбрать вариант или написать свой ответ.

**После действия**
Исходный capture и ответ рассматриваются как одна операция; после применения пользователь возвращается в Today.

**Empty state / Loading / Error**
Draft исходного запроса сохраняется. При ошибке ответ можно повторить без повторного ввода первого запроса.

**Особые состояния**
Clarification не создаёт чат и не накапливает длинную историю. Если после одного вопроса запрос всё ещё небезопасно неоднозначен, система объясняет, чего не хватает, и оставляет draft.

**Что нельзя добавлять**
Длинную анкету, цепочку из пяти вопросов и AI-рассуждения.

### 3.12 Conflict sheet/state

**Цель**
Показать, что все намерения физически не помещаются в план, и получить только необходимое решение пользователя.

**Что пользователь должен понять за 3–5 секунд**
Какие два действия конфликтуют и какой минимальный выбор требуется.

**Контент**
Короткое описание конфликта, затронутые действия, 2–3 решения и свободный текст.

**После действия**
Система строит новый план и возвращает в Today с конкретным plan diff.

**Что нельзя добавлять**
Красный dashboard ошибок, ручной календарный редактор и технические причины scheduler.

### 3.13 Plan Changed confirmation

**Цель**
Подтвердить результат значимого replanning без отдельного экрана.

**Implementation priority:** confirmation с factual diff входит в P0. Общий «Вернуть» требует backend PlanChange rollback и относится к P1; до появления contract mobile не показывает fake Undo.

**Контент**
Компактная строка в Today, например «Зал перенесён на 20:30», и действие «Вернуть».

**После действия**
Timeline уже показывает новый порядок. Undo возвращает предыдущую версию и исчезает после успешного отката.

**Что нельзя добавлять**
Полноэкранный diff, длинное объяснение AI и постоянный баннер.

### 3.14 All Done state

**Цель**
Спокойно показать завершение дня без gamification.

**Контент**

- завершённые строки остаются в timeline приглушёнными;
- в конце появляется короткое «На сегодня всё»;
- свободное время остаётся видимым;
- capture и нижняя навигация остаются доступными.

**Что нельзя добавлять**
Конфетти, streak-pressure, рейтинг продуктивности и большую celebratory card.

## 4. Today — детальная спецификация сверху вниз

### 4.1 Safe area и корневая поверхность

- Экран занимает нативную mobile surface без декоративной рамки устройства.
- Контент начинается ниже status-bar safe area и заканчивается выше home-indicator safe area.
- Референсный горизонтальный gutter — около 22 pt на iPhone; на узкой геометрии допустимо 16 pt.
- Capture и tab bar находятся в нижней thumb zone, но не перекрываются клавиатурой или home indicator.

### 4.2 Header

**Состав:** дата, крупный заголовок «Сегодня», иконка календаря справа.
**Иерархия:** «Сегодня» — главный текст экрана; дата — тихая бордовая contextual-label; календарь — вторичное действие.
**Interaction:** календарь открывает Week; title и дата не являются кнопками.
**Состояния:** при plan changed под header появляется компактная confirmation-строка, а не отдельная карточка.

### 4.3 Focus

Отдельная focus-card не нужна. Фокус кодируется первой текущей строкой timeline:

- label «Сейчас · до 18:00»;
- более крупное название;
- связь с целью;
- мягкая матовая бордовая поверхность;
- тонкая бордовая линия слева;
- текущий круг на timeline имеет бордовую точку.

Это сознательно заменяет dashboard-блоки NOW и UP NEXT.

### 4.4 Timeline

- Один вертикальный временной стержень связывает день.
- Слева от стержня — время.
- На стержне — круг завершения/состояния.
- Справа — кликабельное содержание действия.
- Между действиями — тонкие нейтральные разделители.
- Линия не должна превращаться в плотный calendar grid.

### 4.5 Current task

**Назначение:** единственный главный объект текущего момента.
**Визуально:** крупнее будущих строк, матовый soft-burgundy highlight без тени.
**Tap по содержанию:** Task Details.
**Tap по кругу:** быстрое completion.
**Во время completion:** мягкий pop галочки и приглушение строки; без нового экрана.

### 4.6 Upcoming tasks

- Обычная типографическая строка без отдельной карточки.
- Показываются время, название, короткий goal/context.
- Tap открывает Task Details.
- Круг слева позволяет быстро завершить.
- Ближайшее действие находится выше более поздних; ручной priority-control отсутствует.

### 4.7 Completed tasks

- Круг заполнен графитовым цветом и содержит галочку.
- Название и meta приглушены, но остаются читаемыми как история дня.
- Не переносить автоматически в отдельную секцию «Выполнено».
- Повторный tap не должен случайно создавать новое completion; политика reopen остаётся OPEN для engineering/product review.

### 4.8 Unscheduled

Постоянный Inbox/Unscheduled-раздел **не утверждён** и не должен появляться в P0. Если запрос нельзя безопасно разместить, система должна использовать Clarification или Conflict вместо молчаливого добавления «без времени». Возможная компактная строка «Без времени» — OPEN/P1, не часть final mockup.

### 4.9 Free time и конец дня

«Свободное время» показывается как тихая строка timeline. Это часть плана, а не пустота. После replanning время свободного периода может измениться.

### 4.10 Capture

- Text control: «Что изменилось?» с небольшим `+`.
- Рядом отдельная квадратная кнопка микрофона.
- Оба touch target не меньше 44×44 pt.
- Text открывает Text Capture sheet; microphone — Voice Capture sheet.
- Capture не является tab и не открывает чат.

### 4.11 Bottom navigation

Три пункта: «Сегодня», «Путь», «Профиль». Активный пункт обозначается более тёмным текстом и маленькой бордовой точкой. Иконки для tabs не обязательны и не должны добавляться только ради декора.

### 4.12 Сознательно отсутствующие элементы

- greeting и мотивационная цитата;
- дневной score;
- streak;
- прогресс всех целей;
- dashboard cards;
- фильтры;
- category chips;
- отдельная карточка NOW;
- кнопка «Продолжить»;
- кнопка «Сказать, как вышло»;
- постоянное объяснение, что сделал AI.

## 5. Navigation

### 5.1 Tab navigation

Утверждены ровно три root tabs:

1. **Сегодня** — главный и стартовый экран ежедневного использования.
2. **Путь** — долгосрочные цели и автоматический прогресс.
3. **Профиль** — распорядок, цели, уведомления и данные.

Новые tabs без явного product approval запрещены.

### 5.2 Nested screens

- **Week** открывается кнопкой календаря из Today.
- **Task Details** открывается tap по содержанию task-row.
- **Workout Details** — вариант Task Details для training-task.
- **Onboarding / Мой распорядок** открывается при первом запуске либо из Profile.
- **Первый собранный план** открывается после успешного onboarding processing.

### 5.3 Back behavior

- Week → Today.
- Task/Workout Details → исходный Today.
- «Мой распорядок», открытый из Profile → Profile.
- Первый план → onboarding/routine draft.
- System back/screen-edge swipe на iOS повторяет тот же путь.
- Back не должен уничтожать введённые workout results или capture draft.

### 5.4 Sheets

Как bottom sheets открываются:

- Text Capture;
- Voice Capture;
- Clarification;
- Conflict.

Sheet закрывается pull-down/close только там, где это безопасно. Draft сохраняется до явной отправки либо осознанного discard.

### 5.5 Capture navigation

- Capture запускается с Today и Week; на Path также допустима уже утверждённая доступная точка capture.
- Applied replanning приводит в Today, потому что именно там виден результат.
- Clarification и Conflict остаются поверх текущего контекста, затем applied result открывает Today.

## 6. Text Capture UX

### 6.1 Основной flow

1. Пользователь нажимает «Что изменилось?».
2. Снизу открывается Text Capture sheet.
3. Пользователь вводит естественную фразу.
4. Action «Обновить день» становится доступен только для непустого draft.
5. После отправки action показывает processing, повторная отправка блокируется.
6. Возвращается одно из продуктовых состояний ниже.

### 6.2 Applied

- Sheet закрывается.
- Открывается Today.
- Timeline уже находится в новом состоянии.
- Под header появляется одно конкретное подтверждение, например «Зал перенесён на 20:30».
- Для значимого изменения доступно «Вернуть».

### 6.3 Clarification

- Text sheet сменяется коротким Clarification sheet.
- Исходный draft сохраняется как контекст операции.
- После одного ответа система продолжает исходный запрос, а не создаёт новое сообщение.

### 6.4 Confirmation

Дополнительное подтверждение до применения нужно только для рискованного или необратимого изменения. Обычное replanning применяется сразу и подтверждается результатом плюс Undo. Универсальный шаг «Вы уверены?» запрещён.

### 6.5 Conflict

- Sheet коротко называет конфликтующие действия.
- Показываются 2–3 решения и свободный ответ.
- После выбора система применяет новый план и показывает diff в Today.

### 6.6 Unsupported request

Показывается конкретная граница продукта и ближайшее доступное действие. Пример: «Пока не могу оформить покупку, но могу добавить её в сегодняшний план». Draft остаётся доступным. Не использовать «Я как AI…».

### 6.7 Error

- Sheet остаётся открыт.
- Draft не очищается.
- Processing прекращается.
- Появляется короткое «Не удалось обновить план» и retry.
- Технические коды и stack traces пользователю не показываются.

### 6.8 Draft policy

- Закрытие клавиатуры не очищает draft.
- Временный уход приложения в background не очищает draft.
- После applied draft очищается.
- После explicit cancel допустимо очистить только после понятного discard-действия; точный срок локального хранения остаётся OPEN.

### 6.9 Возврат в Today и plan diff

UI не показывает отдельный экран «AI всё сделал». Результат виден в изменившихся временах и составе timeline. Confirmation сообщает только главное изменение, а не полный машинный diff.

## 7. Voice UX

Voice — способ Capture, а не отдельный режим продукта.

### 7.1 Точки запуска

- microphone рядом с «Что изменилось?» в Today;
- microphone в Week;
- «Записать голос» в onboarding/routine.

Отдельного voice-tab нет.

### 7.2 Recording sheet

Bottom sheet содержит:

- close;
- состояние «Слушаю»;
- «Говорите как обычно»;
- спокойную waveform;
- live/final transcript;
- основное действие «Готово».

### 7.3 Состояния voice flow

1. **Requesting permission:** системный iOS permission flow; до него коротко объясняется практическая причина доступа.
2. **Listening:** waveform движется, transcript появляется по мере распознавания.
3. **No speech:** «Не расслышал. Попробовать ещё раз».
4. **Transcribed:** waveform останавливается, transcript доступен для проверки.
5. **Edit:** исправление остаётся в том же sheet; точный control OPEN, новый экран запрещён.
6. **Confirm:** «Готово» отправляет тот же CaptureRequest, что и текст.
7. **Cancel:** запись и временный аудиобуфер удаляются в соответствии с privacy policy; plan не меняется.
8. **Processing:** sheet остаётся до получения semantic result либо переходит в компактное processing-состояние.
9. **Applied/Clarification/Conflict/Error:** те же продуктовые результаты, что у Text Capture.

### 7.4 Результат

После applied пользователь оказывается в Today и видит изменившийся день. Не показывать transcript как чат-сообщение после применения.

### 7.5 Что запрещено

- полноэкранный AI-assistant;
- orb/avatar;
- voice conversation history;
- ответы голосом по умолчанию;
- отдельная информационная архитектура для voice.

## 8. Adaptive replanning UX

Пример запроса: **«Сегодня задержусь на работе до восьми».**

### 8.1 До

Today показывает:

- текущую рабочую задачу до 18:00;
- тренировку в 19:30;
- ужин в 20:45;
- растяжку в 21:30;
- свободное время в 21:45.

### 8.2 Capture и processing

Пользователь нажимает text или microphone, вводит/говорит фразу и подтверждает.

Во время processing:

- draft/transcript остаётся видимым;
- действие повторной отправки заблокировано;
- интерфейс не показывает chain of thought;
- текущий план не исчезает до получения валидного результата.

### 8.3 После applied

Today показывает:

- текущую работу до 20:00;
- тренировку в 20:30;
- ужин в 21:45;
- растяжка убрана из этого вечера или перенесена системой;
- свободное время в 22:30;
- confirmation «Зал перенесён на 20:30»;
- action «Вернуть».

Изменения проявляются непосредственно в timeline с коротким мягким transition. Полный алгоритмический diff не показывается.

### 8.4 Conflict

Если тренировка, ужин и обязательное действие не помещаются безопасно, система не угадывает жертву. Появляется короткий вопрос, например:

> После работы помещается либо тренировка, либо час английского. Что оставить сегодня?

Варианты: «Тренировку», «Английский», «Ответить своими словами».

### 8.5 Undo

Этот визуальный flow утверждён для mobile v1, но его реализация относится к P1 после появления реального backend rollback contract. В P0 сильные изменения используют существующее confirmation до применения; fake/local-only general Undo запрещён.

- Undo относится к одной последней значимой PlanChange.
- «Вернуть» восстанавливает предыдущую версию timeline.
- Во время отката action временно блокируется.
- Если undo не удалось, новый план не исчезает, а строка показывает retry.
- Срок жизни Undo и серверная retention policy остаются OPEN.

## 9. Clarification UX

Пример capture: **«Добавь БЖУ, чтобы я считал».**

Система не должна угадывать, хочет ли пользователь дневную цель, запись еды или только отображение макронутриентов.

### 9.1 Sheet

**Вопрос:** «Что именно вы хотите считать?»

**Варианты:**

- «Калории и БЖУ за день»;
- «БЖУ каждого приёма пищи»;
- «Ответить своими словами».

Свободный ответ открывает компактное поле в том же sheet. Исходная фраза может быть показана одной тихой строкой контекста, но не chat-bubble.

### 9.2 После ответа

- Ответ связывается с исходным capture.
- Если намерение стало достаточным, изменение применяется.
- Пользователь возвращается в Today или релевантный экран с коротким confirmation.
- Если capability не входит в текущий release, UI честно сообщает границу и не симулирует успех.

### 9.3 Ограничения

- один короткий вопрос за раз;
- 2–3 вариантов, только если они действительно уменьшают неопределённость;
- всегда доступен ответ своими словами;
- нет длинной истории сообщений;
- нет вопроса о том, что можно безопасно вывести из уже известного контекста.

## 10. Task interaction

### 10.1 Checkbox

- Визуальный круг около 26 pt находится внутри touch target минимум 44×44 pt.
- Uncompleted — светлая поверхность и нейтральная граница.
- Current — бордовая граница плюс маленькая бордовая точка.
- Completed — графитовая заливка и светлая галочка.

### 10.2 Tap по task

Tap по содержанию строки открывает Task Details. Checkbox и content — две разные hit areas с разным результатом.

### 10.3 Current task

Current task выделяется типографикой и soft-burgundy подложкой, а не большой CTA-кнопкой.

### 10.4 Completed task

- строка остаётся в контексте дня;
- content становится приглушённым;
- progress связанной цели обновляется;
- отдельный result screen не открывается.

### 10.5 Transition и haptic

- Галочка мягко появляется/pop-in.
- Строка спокойно приглушается.
- На подтверждённом completion — лёгкий success/selection haptic.
- Haptic до успешного local commit не должен обещать сохранение, если приложение не умеет гарантировать локальную очередь.

### 10.6 Error rollback

Допустим optimistic UI только при наличии надёжного локального outbox. При окончательной ошибке:

- checkbox возвращается в предыдущее состояние;
- progress не увеличивается либо откатывается;
- появляется короткое retry-сообщение;
- введённые workout results не теряются.

### 10.7 Task Details

Task Details показывает время, цель и план. Completion выполняется одной нижней кнопкой. Для workout используется «Завершить тренировку».

### 10.8 Неутверждённые interactions

Swipe actions, long press, context menu, drag-and-drop и ручное reorder **не утверждены**. Не реализовывать без отдельного решения.

## 11. Visual language

Ниже только финальная утверждённая система. Старые палитры и экспериментальные шрифты не являются частью handoff.

### 11.1 Light palette

| Token | Value | Usage |
|---|---:|---|
| Canvas | `#E8E9E5` | окружающая техническая поверхность preview; не отдельный фон внутри native screen |
| Paper / App background | `#F8F9F5` | основной фон мобильного приложения |
| Raised surface | `#FDFEFA` | sheet и единичные bounded input surfaces |
| Ink | `#1D1F1C` | основной текст и primary dark actions |
| Muted | `#73766F` | вторичный текст, время, units |
| Rule | `#D2D4CD` | тонкие разделители и inactive timeline |
| Burgundy | `#6B3036` | главный акцент, progress и current state |
| Soft burgundy | `#EEE6E6` | мягкая подложка current task |

Dark palette в интерактивном прототипе существует как exploration, но не проходила отдельное product approval. Полноценный Dark Mode остаётся OPEN/P1.

### 11.2 Typography

- Использовать системную типографику по принципу Telegram-like native UI.
- iOS: системный San Francisco / SF Pro через platform default.
- Android позже: системный Roboto через platform default.
- Разрешённые weights: `400` и `500`.
- Не использовать декоративные web-fonts.
- Время, проценты, вес и повторения используют tabular figures, но не отдельный моноширинный шрифт.
- Крупные заголовки имеют аккуратный отрицательный tracking; production должен уважать Dynamic Type.

### 11.3 Radii

- Обычные controls: около 10 pt.
- Единичная story/input surface: около 14 pt.
- Bottom sheet: около 18 pt по верхним углам.
- Checkbox/avatar markers — круг.
- Не превращать каждую строку в rounded card.

### 11.4 Spacing philosophy

- Базовый ритм кратен 4 pt.
- Основные интервалы: 8, 12, 16, 20, 24 pt.
- Горизонтальный screen gutter: около 22 pt на референсном iPhone, 16 pt на узком экране.
- Whitespace используется для иерархии; экран не заполняется декоративными блоками.

### 11.5 Shadows and surfaces

- Внутри native app экран не имеет device-frame и внешней тени прототипа.
- Обычные строки и секции не имеют теней.
- Bottom sheet получает системную elevation/dimming.
- Raised surface используется только там, где объект действительно является отдельным полем или sheet.

### 11.6 Icons

- Тонкие простые outline/symbol icons.
- Визуальный размер примерно 16–20 pt внутри hit target 44 pt.
- Использовать platform-consistent symbol style; конкретный icon library — OPEN.
- Не использовать sparkles, роботов и декоративный AI-symbolism.

### 11.7 Timeline

- Нейтральная линия 1 pt.
- Круг completion визуально около 26 pt внутри 44 pt target.
- Current marker использует burgundy.
- Время выравнивается табличными цифрами.
- Будущие действия разделяются тонкими правилами.

### 11.8 Progress

- Тонкая нейтральная линия и бордовое заполнение 1–2 pt.
- Небольшой круглый marker.
- Процент крупнее context, но не становится dashboard KPI.
- Изменение анимируется один раз при открытии/обновлении и уважает Reduce Motion.

### 11.9 Current task

- Soft burgundy background.
- Тонкая burgundy line слева.
- Название заметно крупнее upcoming tasks.
- Без тени, градиента и огромной CTA-заливки.

## 12. Design principles — правила реализации

1. **Today-first.** Главная ценность должна быть видна на Today за несколько секунд.
2. **Mobile-native, не mobile website.** Safe areas, sheets, keyboard, haptics и системные transitions являются частью UX.
3. **Результат важнее AI-механики.** Пользователь видит новый план, а не внутренние рассуждения модели.
4. **Не превращать Capture в чат.** Text и voice — короткие входы в действие, без conversation history.
5. **Минимум ручного планирования.** Если намерение можно понять из естественного языка, не добавлять форму, slot picker или priority control.
6. **Один главный объект за раз.** На Today главным является current task, а не набор метрик.
7. **Минимум карточек.** Структуру создают типографика, whitespace, timeline и тонкие rules.
8. **Системная типографика.** Только platform font и weights 400/500.
9. **Один акцент.** Матовый burgundy используется для current state, progress и значимых деталей; не раскрашивать категории.
10. **Факты без оценки.** Невыполненный повтор, перенос или пропуск сохраняются как реальность, а не ошибка пользователя.
11. **AI спрашивает только при критической неоднозначности.** Один короткий clarification предпочтительнее опасной догадки или анкеты.
12. **Every state is recoverable.** Draft, workout result и текущий день не должны теряться из-за сети, background или retry.

## 14. iOS behavior requirements

Это UX-требования, не выбор библиотек.

### 14.1 Safe area

- Header находится ниже status bar/notch.
- Bottom controls и tab bar находятся выше home indicator.
- Sheets учитывают нижнюю safe area.
- Interactive content не попадает под Dynamic Island/system overlays.

### 14.2 Keyboard

- Поле и primary action остаются видимыми при открытой клавиатуре.
- Sheet корректно меняет высоту либо скроллится.
- Interactive dismiss допустим, но не очищает draft.
- Return key behavior соответствует контексту и не отправляет случайно многострочный рассказ.

### 14.3 Bottom sheets

- Нативная modal-подача снизу.
- Dimming остаётся спокойным.
- Pull-to-dismiss разрешён только при сохранении draft или безопасном discard.
- Voice recording не должна продолжаться незаметно после dismiss.

### 14.4 Gestures

- Standard edge-swipe back для nested screens.
- System scroll physics.
- Swipe/long press на tasks не являются продуктовым требованием.
- Gesture не должен быть единственным способом выполнить важное действие.

### 14.5 Haptics

- лёгкий haptic при подтверждённом completion;
- мягкий haptic при применённом значимом PlanChange допустим;
- error haptic только при ошибке, требующей внимания;
- не использовать haptics декоративно на каждом tap.

### 14.6 Touch targets

- Минимум 44×44 pt для buttons, checkbox hit areas и icon actions.
- Визуальный icon/checkbox может быть меньше hit area.
- Между соседними hit areas достаточно пространства для одной руки.

### 14.7 Dynamic Type

- Поддерживать системное увеличение текста.
- При больших размерах строки могут становиться выше, но не обрезаться.
- Primary actions и labels не должны превращаться в clipped one-line text.
- Timeline перестраивается, а не уменьшается ниже читаемого размера.

### 14.8 VoiceOver

- Checkbox объявляет task name и состояние.
- Task content и checkbox — разные accessibility actions.
- Timeline order совпадает с чтением сверху вниз.
- Progress объявляет цель, процент и последнее действие.
- Waveform декоративна; voice state и transcript имеют текстовые labels.
- PlanChanged confirmation и errors объявляются как соответствующие live updates без повторного чтения всего экрана.

### 14.9 Reduce Motion

- Отключает waveform animation, check pop и animated progress movement.
- Состояния меняются мгновенно, но остаются понятными.
- Никакая информация не зависит только от движения.

## 16. P0 / P1 / Later

### P0 — первый живой iOS dogfooding

Цель P0 — проверить уже поддержанный backend vertical slice на реальном iPhone, не реализуя весь утверждённый mobile vision.

- Нативный iOS shell с Today как стартовым экраном.
- Загрузка atomic Today snapshot из существующего Mobile API v1.
- Today с focus/current, scheduled, completed и честным unscheduled/conflict состоянием, совместимым с текущим contract.
- Text Capture с client-generated request id и безопасным retry.
- Результаты capture: applied, clarification required, confirmation required, conflict, no change, unsupported и failed.
- Ответ на persistent clarification/confirmation/conflict.
- Factual PlanDiff и атомарное применение нового DaySnapshot.
- Quick task completion `planned ↔ done` с согласованным snapshot.
- Минимальный Task Details только из уже доступных task данных, без нового backend slice.
- Loading, timeout, offline cache/draft и recoverable error states.
- Accessibility minimum: safe area, keyboard, 44 pt targets, VoiceOver labels, Dynamic Type, Reduce Motion.

**Не входит в P0:** onboarding/first-plan UI, Week, Path, Profile mutations, Voice/STT, general Undo, workout tracker, goal percentages, integrations, complex recurrence и Android-specific polish. Visual design этих экранов зафиксирован в handoff, но их реализация не должна блокировать первый Today dogfooding.

### P1 — после стабильного P0

- Onboarding/routine narrative и экран первого собранного плана поверх отдельного согласованного contract slice.

- General PlanChange Undo после backend rollback contract.
- Базовый Workout Details с editable set results и local draft после отдельного workout contract.
- Push/notification behavior после product review.
- Calendar/Health integrations при наличии подтверждённой ценности.
- Редактирование/пересмотр training program как отдельный осознанный flow.
- История тренировок и сравнение фактических результатов без оценочного тона.
- Более полный Profile/settings.
- Dark Mode после отдельного visual QA.
- Background sync/outbox hardening и расширенные recovery states.
- Простые recurrent constraints, если backend уже поддерживает их безопасно.

## 17. Backend capabilities required by design

Этот раздел не задаёт endpoints, transport или внутреннюю архитектуру. Он фиксирует только продуктовые возможности, которые mobile UI ожидает получить.

### 17.1 Получить Today

**Mobile UX expects:** воспроизводимый snapshot текущего дня, пригодный для timeline и offline cache.
**Input:** пользователь, локальная дата/timezone, опциональная известная версия плана.
**Output needed:** версия DayPlan, дата, timezone, current/upcoming/completed actions, start/end times, free time, связи с goals, sync metadata.
**Why UI needs it:** Today является главным экраном и должен однозначно отрисовать порядок и состояния без собственного планирования.

### 17.2 Получить Week

**Mobile UX expects:** read-only обзор семи дней с состояниями действий.
**Input:** пользователь, диапазон дат, timezone, опциональные версии cache.
**Output needed:** дни и компактные task summaries с time/status/goal reference.
**Why UI needs it:** Week переключает выбранный день, не рассчитывая расписание на клиенте.

### 17.3 Создать первый план из narrative

**Mobile UX expects:** превратить один рассказ в первый понятный plan preview либо запросить clarification.
**Input:** текст рассказа, timezone, locale, доступный user context.
**Output needed:** semantic result: applied plan preview, clarification, unsupported или error; цели, cadence и базовый ритм при success.
**Why UI needs it:** onboarding не содержит ручной формы, поэтому server capability должна вернуть готовую продуктовую структуру.

### 17.4 Отправить natural-language Capture

**Mobile UX expects:** одна операция, которая может применить изменение, запросить уточнение или вернуть конфликт.
**Input:** текст/transcript, source context (Today/Week/Onboarding), current plan version, locale/timezone, idempotency context.
**Output needed:** typed semantic result: applied, clarification, conflict, unsupported или error; correlation/operation identity.
**Why UI needs it:** Text и Voice используют один Capture flow и не должны разбирать свободный язык на клиенте.

### 17.5 Получить Clarification

**Mobile UX expects:** один короткий вопрос с небольшим набором понятных вариантов и возможностью free text.
**Input:** исходный CaptureRequest и известный user/plan context.
**Output needed:** question, answer choices, free-text allowance, continuation identity, срок валидности.
**Why UI needs it:** мобильный sheet должен быть компактным и продолжить именно исходную операцию.

### 17.6 Ответить на Clarification

**Mobile UX expects:** продолжить исходный capture без создания chat history.
**Input:** continuation identity, выбранный option или free text, current plan version.
**Output needed:** applied PlanChange, следующий необходимый conflict/clarification либо typed error.
**Why UI needs it:** после одного ответа UI должен либо показать результат, либо честно остановиться, не угадывая.

### 17.7 Получить и применить PlanChange/plan diff

**Mobile UX expects:** новый authoritative DayPlan плюс короткая человекочитаемая summary для confirmation.
**Input:** capture/clarification result и базовая plan version.
**Output needed:** previous/new version references, новый DayPlan snapshot, структурированный diff затронутых действий, короткая summary, возможность undo.
**Why UI needs it:** timeline обновляется из нового snapshot, а confirmation показывает только главное изменение.

### 17.8 Undo PlanChange

**Mobile UX expects:** безопасно вернуть одну последнюю значимую операцию.
**Input:** PlanChange identity, current version/idempotency context.
**Output needed:** restored DayPlan snapshot, новая authoritative version или conflict/error.
**Why UI needs it:** «Вернуть» не должно реконструировать старый план на клиенте.

### 17.9 Complete task

**Mobile UX expects:** завершить действие quick checkbox или кнопкой details и получить подтверждённое состояние.
**Input:** task identity, task/plan version, completion time, optional factual result, idempotency context.
**Output needed:** updated task status, authoritative DayPlan version, related goal progress delta/current value, sync status.
**Why UI needs it:** checkbox, timeline и Path должны обновиться согласованно и уметь откатиться при ошибке.

### 17.10 Сохранить Workout result

**Mobile UX expects:** сохранять фактический вес/повторения без оценки соответствия плану.
**Input:** workout/task identity, exercise and set identities, factual values, draft/final status, timestamps.
**Output needed:** saved workout snapshot/version, completion state, related goal update, validation только формата/диапазона.
**Why UI needs it:** set rows редактируются в течение тренировки и должны переживать навигацию/offline.

### 17.11 Получить Goals/Path

**Mobile UX expects:** три активные цели, простой progress и источник последнего изменения.
**Input:** пользователь, опциональная known version.
**Output needed:** goal identity/title/type, current progress, stages/labels, last delta and source.
**Why UI needs it:** Path отображает authoritative progress и не рассчитывает его из локальных эвристик.

### 17.12 Получить/обновить Profile context

**Mobile UX expects:** загрузить narrative/routine и доступность настроек.
**Input:** пользователь.
**Output needed:** display name, current routine narrative/version, active-goal count, capability/integration availability.
**Why UI needs it:** Profile не должен показывать ложные активные integrations и должен открывать актуальный рассказ.

### 17.13 Voice transcription

**Mobile UX expects:** получить transcript для проверки до semantic Capture.
**Input:** разрешённый audio input/stream и locale.
**Output needed:** partial/final transcript, confidence/recognition state, typed no-speech/error; privacy/retention contract.
**Why UI needs it:** waveform и transcript должны иметь реальные состояния, а text/voice semantic processing оставаться единым.

### 17.14 Sync/recovery metadata

**Mobile UX expects:** различать authoritative, pending-local, conflict и failed состояния.
**Input:** local operation/version identifiers.
**Output needed:** stable identities, versions, idempotency behavior, server timestamps, retryability, conflict representation.
**Why UI needs it:** offline completion, workout drafts и retry не должны дублировать операции или терять факты.

### 17.15 Error and unsupported taxonomy

**Mobile UX expects:** преобразовать backend result в понятное и recoverable UI-state.
**Input:** failed capability invocation.
**Output needed:** machine-readable category, retryable flag, safe user-facing summary or localization key, preserved continuation/draft context.
**Why UI needs it:** mobile не должен парсить случайные строки и показывать технические ошибки.

## 18. Locked vs Open decisions

### LOCKED

Следующие решения Engineering/Mobile Agent не меняют без явного согласования владельца продукта:

- основной продукт — mobile app, первый клиент iOS;
- Today — стартовый и главный экран;
- root navigation: «Сегодня / Путь / Профиль»;
- Week открывается из Today через календарь, не является tab;
- Tap по task открывает details; круг слева быстро завершает;
- Task Details заканчивается «Завершить задачу», Workout — «Завершить тренировку»;
- после completion нет дополнительного итогового экрана;
- Text и Voice являются Capture, а не chat;
- applied replanning проявляется в Today и коротком confirmation плюс Undo;
- при критической неоднозначности задаётся один короткий clarification;
- timeline-based Today без dashboard, drag-and-drop и ручных priority controls;
- базовый workout logging хранит фактические sets без оценки пользователя;
- Path обновляется автоматически из выполненных действий;
- финальная light palette, system typography, weights 400/500 и restrained burgundy language;
- отсутствие AI sparkles/avatar/chain of thought;
- утверждённое разделение P0/P1/Later;
- Web/Telegram/Obsidian не входят в текущий спринт и не определяют mobile UX.

### OPEN

Следующие вещи не являются утверждёнными design decisions и могут быть предложены Engineering Agent с объяснением trade-offs:

- mobile framework и project structure;
- transport/API implementation details и конкретные endpoint names;
- auth mechanism и session lifecycle;
- local database/cache technology;
- state-management library;
- networking/retry/outbox implementation;
- audio capture and transcription implementation/provider;
- push provider;
- analytics/crash reporting stack;
- exact idempotency/versioning mechanism;
- точный срок хранения draft и Undo;
- exact control редактирования voice transcript внутри sheet;
- reopen/uncomplete policy для completed tasks;
- icon implementation/library при сохранении утверждённого внешнего языка;
- Dark Mode implementation и финальная dark palette после отдельного review;
- P1 integrations и permission sequencing;
- production scheduler/AI internals, если mobile contract соблюдён.

Open decision не разрешает менять user-visible behavior, locked visual hierarchy или расширять P0.

## 19. Acceptance journey — первый релиз

Этот сценарий является продуктовой историей для приёмки полного mobile v1. Первый P0 dogfooding принимает более узкий Today vertical slice из раздела 16 и не блокируется P1-экранами.

### 19.1 Первый запуск

Матвей открывает приложение на iPhone. Вместо dashboard он видит «Расскажите, как вы живёте», короткое объяснение и выбор voice/text. Для P0 он выбирает текст.

### 19.2 Рассказ

Он пишет:

> Работаю по будням с 10 до 18. После работы могу заниматься собой. Хочу за год стать Senior iOS-разработчиком, набрать 6 кг и сесть на шпагат.

Draft переживает keyboard dismiss и background. Матвей нажимает «Собрать мой план».

### 19.3 Первый план

После короткого «Собираю план…» появляется «Ваш ритм на август»: три цели, разумная недельная частота и базовый вечер. Матвей понимает план без чтения AI-объяснений и нажимает «Начать».

### 19.4 Today

Today сразу показывает current task «Архитектура модуля», затем тренировку, ужин, растяжку и свободное время. Матвей понимает день за несколько секунд.

### 19.5 Выполнение задачи

Он tap по current task, читает последовательный план и нажимает «Завершить задачу». Приложение возвращается в Today; круг заполнен, строка приглушена. Path для Senior обновлён без отдельного result screen.

### 19.6 Workout fact

Позже Матвей открывает тренировку. В четвёртом подходе жима он делает 5 повторений вместо 6 и оставляет фактическое значение `5`. Приложение не оценивает его и сохраняет факт. После «Завершить тренировку» он возвращается в Today.

### 19.7 Изменение дня

Матвей нажимает «Что изменилось?» и пишет:

> Сегодня задержусь на работе до восьми.

После processing Today показывает работу до 20:00, зал в 20:30, ужин позже и свободное время в 22:30. Под header — «Зал перенесён на 20:30» и «Вернуть».

### 19.8 Clarification

Матвей вводит:

> Добавь БЖУ, чтобы я считал.

Вместо догадки появляется один вопрос «Что именно вы хотите считать?» с тремя ответами. Матвей выбирает «Калории и БЖУ за день». Если capability доступна, изменение применяется; если не входит в P0, приложение честно сообщает границу, сохраняя draft.

### 19.9 Продолжение дня

Матвей возвращается в Today и продолжает действовать по новому timeline. Ему не пришлось вручную передвигать слоты, выбирать приоритеты или вести разговор с AI.

### 19.10 Acceptance outcome

Сценарий принят, если все шаги работают на реальном iPhone, переживают краткий offline/background, не теряют drafts/results и соответствуют утверждённому visual hierarchy.

# PROMPT FOR ENGINEERING AGENT

Ниже готовый prompt. Передавать его Engineering Agent вместе с полным документом выше.

```text
Ты — основной Engineering Agent проекта AI Life Planner. Твоя зона ответственности в этом спринте: существующий backend, API и системная архитектура, необходимая для первого iOS dogfooding.

Продуктовый source of truth

Прочитай целиком документ «AI Life Planner — Mobile Product & Design Handoff v1», приложенный к этой задаче. Считай его единственным утверждённым источником mobile product behavior, scope и visual/interaction expectations.

Не переосмысливай продукт и не меняй LOCKED decisions. OPEN engineering decisions разрешено принимать только после изучения существующего repo и с явным объяснением trade-offs.

Твоя задача

1. Прочитать существующий repository целиком в части, релевантной backend/API/architecture.
2. Найти фактический backend, его framework, entrypoints, модели, storage, migrations, auth, background jobs, AI/provider integrations, tests и документацию.
3. Сохранить существующий backend и его рабочую архитектуру. Не создавать второй backend и не переписывать систему без доказанной необходимости.
4. Сопоставить существующие capabilities с разделом «Backend capabilities required by design».
5. Определить, что уже реализовано полностью, частично или отсутствует.
6. Подготовить «Mobile API Contract v1» для P0 iOS dogfooding.
7. Реализовать только необходимые backend/API P0 gaps.
8. Добавить или обновить tests, подтверждающие mobile contract, idempotency, versioning/conflict behavior и сохранение фактических результатов.
9. Не создавать mobile UI в этой задаче.

Жёсткие ограничения

- Не менять mobile design.
- Не добавлять новые product screens, tabs, flows или fields.
- Не расширять P0 возможностями из P1/Later.
- Не развивать Web UX.
- Не развивать Telegram UX.
- Не заниматься Obsidian в текущем спринте.
- Не привязывать mobile contract к конкретному AI provider, если существующая архитектура этого не требует.
- Не переносить scheduler/business rules на будущий mobile client.
- Не выдумывать endpoint names до аудита существующих conventions.
- Не удалять и не ломать существующие consumers без compatibility plan.
- Не начинать новый mobile client и не писать mobile components.

Порядок работы

Этап 1 — Repository audit

- Определи repo roots и текущую branch/worktree state.
- Найди backend entrypoints и реальный runtime.
- Найди API routers/controllers, schemas, domain models, persistence, migrations, auth и tests.
- Найди существующие mobile/web/telegram consumers только для анализа compatibility; не развивай их.
- Найди OpenAPI/contract generation, если она уже есть.
- Найди AI/natural-language/scheduler capabilities и их фактические границы.
- Зафиксируй evidence с точными file paths и символами.

Этап 2 — Capability coverage matrix

Для каждой mobile capability из handoff создай строку:

Capability | P0/P1/Later | Existing evidence | Coverage (Full/Partial/Missing) | Gap | Proposed action

Обязательно проверить:

- Today snapshot;
- initial plan from narrative;
- natural-language Capture;
- typed semantic result: applied/clarification/conflict/unsupported/error;
- answer clarification;
- authoritative PlanChange/plan diff;
- Undo;
- task completion;
- workout set results как P1 gap;
- goal progress как P1 gap до появления достоверной модели;
- profile/routine context как P1 contract slice;
- local/mobile sync requirements: stable IDs, versions, idempotency, retryability;
- Week, voice transcription и general Undo как P1 gaps, не блокирующие P0.

Этап 3 — Mobile API Contract v1

Подготовь контракт, используя существующие naming/conventions проекта. Не обязан создавать REST endpoints, если repo уже использует другой подход, но contract должен однозначно описывать:

- request/response schemas;
- stable identifiers;
- timestamps и timezone semantics;
- versioning/concurrency behavior;
- idempotency для mutations;
- typed result union для Capture;
- PlanChange и structured diff;
- Undo semantics;
- task/workout completion payloads;
- goal progress update representation;
- offline/retry expectations;
- error taxonomy и retryable flag;
- auth assumptions;
- privacy boundaries для narrative/audio/transcript;
- backward compatibility с существующими clients.

Contract не должен заставлять mobile client:

- вычислять расписание;
- парсить естественный язык;
- угадывать тип результата по строке;
- пересчитывать goal progress;
- реконструировать старый plan для Undo.

Этап 4 — P0 gap plan

Составь минимальный implementation plan только для фактически обнаруженных P0 backend gaps. Текущий P0 vertical slice ограничен сценарием:

GET Today
→ Text Capture с idempotent request id
→ applied / clarification / confirmation / conflict
→ atomic DaySnapshot + factual PlanDiff
→ task status planned ↔ done.

Если audit подтверждает, что capability уже реализована и протестирована, не переписывай её. Onboarding, Week, Path, Profile mutations, Voice/STT, general Undo, workout tracker и goal progress contract относятся к P1 и не должны превращаться в P0 backend gaps.

Не включай advanced analytics, complex recurrence, broad integrations, Android polish, Web/Telegram/Obsidian.

Этап 5 — Implementation

После аудита и contract/gap plan реализуй необходимые P0 backend gaps в существующей архитектуре.

- Следуй текущим conventions.
- Делай изменения небольшими и тестируемыми.
- Сохраняй compatibility либо явно реализуй migration/versioning.
- Добавь contract/domain tests для каждого mutation/result state.
- Проверь duplicate requests и retry.
- Проверь stale plan version/conflict.
- Проверь undo.
- Проверь, что factual workout result 5 вместо plan 6 сохраняется как валидный факт.
- Не симулируй success для unsupported capability.

Обязательный результат твоей работы

1. Repo/architecture audit с evidence.
2. Capability coverage matrix.
3. Mobile API Contract v1.
4. P0 gap list с приоритетами.
5. Реализованные необходимые P0 backend gaps.
6. Tests и команды их запуска с фактическим output.
7. Список OPEN engineering decisions и принятых решений.
8. Handoff для будущего Mobile Agent: как подключиться к контракту, без создания UI.

Первый ответ до изменений

Кратко сообщи:

- какой backend и architecture найдены;
- какие mobile/backend capabilities уже видны;
- какие участки repo будешь исследовать дальше;
- какие блокеры существуют, если они реальны.

После этого продолжай аудит и работу самостоятельно. Не останавливайся после общего плана, если нет реального блокера. Любые утверждения о готовности подтверждай свежими test/verification outputs.
```
